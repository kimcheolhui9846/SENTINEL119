# 개발·리뷰·브랜치 규칙

## 브랜치 역할

| 브랜치 | 용도 | 반영 조건 |
| --- | --- | --- |
| `main` | 리뷰와 검증이 끝난 안전한 기준 버전 | 팀원 리뷰를 마친 변경을 merge commit으로 반영 |
| `dev` | 기능 통합과 팀원 리뷰 | 기능 브랜치의 변경을 통합하고 함께 실행·검토 |
| `type/description-yyyymmdd` | 개별 기능·수정·문서 작업 | 최신 `dev`에서 만들고 `dev`로 병합 |

`dev`는 검토 중인 변경이 포함될 수 있으므로 안정 버전으로 간주하지 않는다. 데모·제출에 사용하는 기준 commit과 branch는 실제 검증한 것으로 명시한다.

## 기본 흐름

1. 최신 `dev`에서 작업 브랜치를 만든다. 예: `feat/turn-replay-20261119`, `fix/stale-response-20261119`, `docs/submission-guide-20261119`.
2. 작업 브랜치에서 구현하고 변경에 맞는 검사를 수행한다. 변경 목적·검증 결과·남은 문제를 정리한다.
3. `dev`를 대상으로 PR을 만들고 merge commit으로 통합한다. 팀원은 PR과 통합된 실행 결과를 검토한다.
4. 통합 상태의 목표 동작·회귀·제출 경로를 확인한다. 리뷰 후 수정한 부분도 다시 검토 대상에 포함한다.
5. `dev`에서 `main`으로 반영할 **전체 차이**가 리뷰·검증됐을 때 승격 PR을 병합한다.
6. 승격 후 `main`을 `dev`에 다시 동기화하고, 이후 작업 브랜치는 갱신된 `dev`에서 시작한다.

```text
dev -> feat/... -> dev (통합·팀원 리뷰) -> main (검증된 버전)
                    ^                       |
                    +------ 동기화 ---------+
```

## main 반영 기준

- 작성자 외 팀원 한 명이 반영할 변경 범위를 검토한다.
- 변경에 필요한 검사가 통과하고, 미해결 문제와 미검증 항목이 명시돼 있다.
- `dev`에 미검토 변경이나 깨진 변경이 남아 있으면 전체 `dev` 승격을 미룬다. 일부 기능의 리뷰 완료를 전체 변경의 승인으로 간주하지 않는다.
- `main`에서 직접 개발하거나 force-push하지 않는다. 수정도 기본적으로 `dev`에서 분기한 작업 브랜치를 거친다.
- PR은 merge commit 방식으로 병합한다. 로컬 병합은 `--no-ff`를 사용하고 squash는 하지 않는다.

GitHub의 `main` 보호 설정은 PR 병합·다른 팀원 1명 승인·force-push 차단을 기본 권장안으로 한다. 필수 CI는 실제로 구성하고 확인한 검사만 지정한다. **이 문서 작성으로 원격 보호 설정이 적용된 것은 아니다.**

## 커밋·초기화

- 커밋은 간결한 영어 Conventional Commits를 사용한다. 예: `feat: add turn replay`.
- 첫 커밋은 예외적으로 정확히 `Initial commit`으로 작성한다.
- AI coauthor trailer나 AI 서명을 추가하지 않는다.
- 최초 초기화에서는 공유할 기준 파일을 팀원이 검토한 뒤 `main`에 첫 커밋을 만들고, 같은 기준점에서 `dev`를 생성한다. 이후에는 위 PR 흐름을 적용한다.

원격의 기본 브랜치는 `main`, 협업 통합 브랜치는 `dev`로 유지한다. 작업 시작 시 현재 브랜치와 upstream을 확인하고, 기능 브랜치의 PR 대상은 `dev`로 설정한다.
