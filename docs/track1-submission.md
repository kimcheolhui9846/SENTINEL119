# Track 1 평가 기준과 제출 체크리스트

확인일: 2026-11-19. 출처: 주최 측 `Trillion_Hackathon_2026_안내자료.pdf`(23쪽). 아래 쪽 번호는 PDF 첫 페이지를 1쪽으로 센다. **주최 측 요구사항**과 **SENTINEL119의 준비 계획**을 구분한다. 현재는 문서 정리 단계이며 발표자료·실행 로그·데모가 제출됐다는 뜻이 아니다.

## 1. 공식 평가 기준

Track 1은 AI 에이전트 개발 트랙이며 심사위원 평가 **100점**이다. 필수 조건은 **System 1 판단(빠른 진단·라우팅·검증)에 Zoro-1을 사용하는 것**이다. (PDF 3-4쪽)

| 구분 | 배점 | 공식 평가 내용 | SENTINEL119에서 보여줄 증거: 준비 계획 |
| --- | ---: | --- | --- |
| 창의성 | 50 | 실제 적용 가능성·사업화 | 수보자의 의사결정 보조 문제, 턴별 조기 확정·대기, 기존 관제 흐름에 붙이는 방식과 도입 검증 과제 |
| 완성도 | 15 | 목표 달성 | 신고 입력부터 유형·긴급도·차량·병원 후보까지 연결된 실행 |
| 완성도 | 15 | 오류 시에도 동작 | API timeout·정보 없음·정정·모델 실패를 구분하고 대기·재시도·표시된 저장 정보로 이어지는 처리 |
| 완성도 | 15 | 라이브 데모 | 심사위원이 직접 열 수 있는 데모와 실제 Zoro 추론, 후보 상태 변경에 따른 결과 갱신 |
| 완성도 | 5 | 발표 | 5분 안에 문제·차별성·실제 동작·근거·적용 가능성을 전달 |
| 합계 | 100 | 창의성 50 + 완성도 50 | 공식 배점과 자체 모델 성능 지표를 구분 |

SFT·PPO 수행 여부나 macro-F1·지연시간에 대한 별도 공식 배점은 안내자료에 없다. SFT는 프로젝트 기준선 목표이고 PPO는 사용자가 원하는 추가 실험이다. 모델 비교 지표는 목표 달성과 설계 근거를 뒷받침하는 자체 증거로 사용한다. Track 2의 품질 통과·실행시간 순위 기준은 이 프로젝트에 적용하지 않는다.

프로젝트의 System 1 경로는 **Zoro의 출동유형·긴급도 판단과 후보 비교**다. 별도 PPO gate를 추가해도 Zoro 사용을 대체하지 않는다. 모델명·revision·현재 prefix·응답·판단 채택을 로그로 연결한다. 녹화·기록 재생과 실시간 추론은 화면에서 구분한다.

## 2. 공식 제출물

### 발표자료: Google Slides

주최 측 요구사항은 다음과 같다. (PDF 9-10쪽)

- 5분 발표에 맞춰 **5장 내외**로 구성한다.
- **Google Slides 필수**이며 PPTX/PDF 등 다른 형식으로 제출할 수 없다.
- **주최 측 제공 Google Slides 템플릿**을 사용한다. 프로젝트명·팀명을 수정하고 장표는 자유롭게 추가할 수 있다.
- 파일명은 `발표순서_트랙_팀명`. 발표순서는 두 자리 `01`-`28`, Track 1은 `T1`이다. 예: `03_T1_팀명`.
- 추첨 결과에 맞춰 파일명을 바꾸고 지정 Google Drive 폴더에 제출한다.

## 3. 3종 실행 로그와 시연 계획

| ID | 시나리오 | 보여줄 동작 | 제출 파일 |
| --- | --- | --- | --- |
| S1 | 성북구 장위동 심정지 의심 | 태스크별 다른 확정 시점, 심정지 확정 후 펌뷸런스 추가 배차, 주증상 확정 전 병원 미리 추천 | `docs/submission/logs/scenario-01.jsonl` |
| S2 | 영등포구 당산동3가 빌라 화재 | 구급 외 유형의 다중 차량 배차 | `docs/submission/logs/scenario-02.jsonl` |
| S3 | 강남구 삼성동 흉통 + 장애 주입 | 병원 API timeout과 판단 서버 연결 실패를 주입, 보류·재시도·복구 | `docs/submission/logs/scenario-03.jsonl` |

계획 단계에서는 세 시나리오를 모두 구급으로 잡았지만, 출동유형 분기를 보여주기 위해 S2를 화재로 바꿨다. 차량 후보 변경(기존 S2)은 이전 관제 콘솔(`/#console`)의 강변 시나리오에서 확인한다. 제출 로그에는 실제 Zoro 입력·출력, 사용한 지침·후보 상태, API 상태와 복구 동작을 남긴다. S3의 의도적으로 주입한 오류는 주입 여부를 명시한다.

로그는 실행 후 생성한다. 계획한 결과나 손으로 만든 응답을 실제 실행 로그로 제출하지 않는다. 공유 가능한 합성 데모 입력을 우선 사용하고 실제 데이터에서 선별할 경우 개인정보·재배포 범위를 확인한다. 일반 디버그 로그 전체를 제출하지 않는다.

`/logs/`, `/runs/`, `/outputs/`의 원본 실험 산출물은 계속 Git에서 제외한다. 검토한 제출용 JSONL만 `docs/submission/logs/`에 두고 추적한다. 영상·대용량 가중치는 이 폴더에 넣지 않는다.

## 4. 5분 발표 구성안

다음은 제공 템플릿에 적용할 내부 구성안이다. 실제 Google Slides가 만들어졌다는 뜻은 아니다.

| 장표 | 시간 | 핵심 내용 |
| --- | ---: | --- |
| 1. 문제와 적용 대상 | 40초 | 119 신고가 불완전한 상태에서 시작한다는 문제, 관제 보조 사용자와 목표 |
| 2. 해결 방식과 Zoro | 50초 | System 1 판단 경로, 태스크별 WAIT/COMMIT, 지침·자원·병원 연결 |
| 3. 라이브 데모 | 120초 | S1 전체 흐름, S2 후보 변경, S3 오류 대응의 핵심 장면 |
| 4. 완성도와 실행 증거 | 50초 | 3종 로그, 실제 측정 지연·오판·완주 결과, 구현 범위와 남은 한계 |
| 5. 적용 가능성과 확장 | 40초 | 기존 시스템 연동 방식, 시범 도입·검증 단계와 사업화 가설 |
| 합계 | 300초 | 5분 |

사업화와 실제 적용은 계획·가설로 표시한다. 검증하지 않은 효과, 도입 기관, 임상 정확도나 시간 절감 수치를 만들지 않는다. SFT/PPO 결과는 측정된 경우에만 장표 4에 넣고, 학습 방법 설명이 라이브 데모 시간을 잠식하지 않도록 한다.

## 5. 마감·환경 조건

- **2026-11-20 09:00 제출 마감**. 08:00 재집합, 09:00-09:30 발표 준비, 09:30-12:00 발표·심사다. (PDF 16쪽)
- Track 1은 팀당 **100달러 Brev 크레딧**을 제공하며 L40S를 권장한다. 크레딧 내에서 GPU 선택은 자유다. **사용 기한은 해커톤 종료일 당일이며 이후 접근 불가, 추가 크레딧 제공 불가**로 안내돼 있다. (PDF 7쪽)
- 기존 코드 사용을 허용하고, 코드 공개 관련 안내에 `Apache-2.0`이 표기돼 있다. 실제 재사용 코드의 출처·라이선스 표기는 별도로 보존한다. (PDF 2쪽)

내부 준비 계획: 심사 시간에 데모가 접근 가능하도록 잔액과 인스턴스를 점검하고, 종료 전 재실행에 필요한 코드·환경·공유 가능한 로그·학습 산출물 보관 위치를 확보한다. 기록 재생과 영상은 장애 대비 보조 자료이며, 라이브 데모 요구를 충족했다고 자동 간주하지 않는다.
